i benchmark storici acquisiti il 21/10/2026.


5. ESECUZIONE DELLA PIPELINE OPERATIVA (DISCOVERY -> DETECTION -> CONSISTENCY)
--------------------------------------------------------------------------------
La pipeline reale deve operare con gli alias deterministici attivi (`E001..En`)
e con il retry limitato abilitato.

Passaggio 5.1: Esecuzione Sintetica di Controllo (Demo / End-to-End preliminare)
Prima di processare i messaggi reali, validare il flusso su un set sintetico:
```bash
python3 -c "
from analysis.service import LocalTopicAnalysisService
from ai.lmstudio import LmStudioClient
from analysis.models import OperationalProfile

print('Avvio test preliminare sintetico...')
# Inizializzazione del client LM Studio e del service
client = LmStudioClient(
    base_url='http://localhost:1234',
    model_id='qwen2.5-7b-instruct',
    default_timeout_seconds=30.0,
)
service = LocalTopicAnalysisService(client=client)
print('Client LM Studio e LocalTopicAnalysisService inizializzati con successo.')
"
```

Passaggio 5.2: Avvio Topic Discovery Operativa
Avviare l'elaborazione dei chunk (26 chunk previsti per il dataset autorizzato):
- Monitorare il log per verificare che per i chunk non compaiano UNKNOWN_ERROR/GENERIC_ERROR non gestiti.
- CONTRATTO DI RETRY ED ERRORI HTTP:
  * Errori permanenti HTTP 400 (parametri non validi, schema JSON rifiutato, context overflow non risolvibile
    a livello di chunk): il sistema fallisce chiuso immediatamente (FAIL-CLOSED, zero retry, attempts = 1)
    senza sprecare compute su richieste non recuperabili.
  * Errori transienti (HTTP 502/503/504, HTTP 429 rate limit o timeout di backend) ed errori di output
    strutturato (AiStructuredOutputError da parsing o risposte troncate): il sistema applica un singolo
    retry controllato (attempts = 2) con registrazione fedele del conteggio tentativi e token cumulati.

Passaggio 5.3: Avvio Topic Detection Operativa
- Verificare che ciascun chunk utilizzi alias biiettivi locali (`E001..En`).
- Se il modello tenta di citare un ID non ammesso o in formato non conforme, scatterà il
  retry guidato che fornisce ESCLUSIVAMENTE la lista degli alias validi per quel chunk.
- Verificare nei log che i tentativi per chunk siano tracciati fedelmente (`attempts = 1` o `attempts = 2`).

Passaggio 5.4: Valutazione della Consistenza Semantica Indipendente
- Al termine della Detection, il servizio `ConsistencyService` valuta la concordanza semantica
  in un'inferenza separata e deterministica, senza contaminazione tra Discovery e Detection.
- Se la Detection si conclude con stato `PARTIAL`, il report di consistenza marcherà
  esplicitamente `consistency_completeness = 'PARTIAL'` con avviso forense.

6. RACCOLTA ED ESPORTAZIONE DEI REPORT JSON (VERIFICA METRICHE E PRIVACY)
--------------------------------------------------------------------------------
All'atto dell'esportazione:
- Verificare che `execution_software_commit` sia valorizzato con il commit Git effettivo
  che ha eseguito l'inferenza (non più `NOT_RECORDED`).
- Verificare che `execution.error_count` corrisponda al numero reale di fallimenti:
  se 2 chunk falliscono, `error_count` DEVE essere >= 2.
- Verificare che nessun testo privato di messaggio sia trapelato nelle sezioni diagnostiche.
- I codici di errore devono appartenere esclusivamente all'allowlist sicura (nessun trace non filtrato).

Comando di validazione JSON esportato:
```bash
python3 -c "
import json, sys

path = sys.argv[1] if len(sys.argv) > 1 else 'latest_run.json'
with open(path, 'r', encoding='utf-8') as f:
    data = json.load(f)

exec_commit = data.get('execution_software_commit')
err_count = data.get('execution', {}).get('error_count', 0)
failed_chunks = len([c for c in data.get('chunk_diagnostics', []) if c.get('status') == 'FAILED'])

print(f'Execution Git Commit: {exec_commit}')
print(f'Execution Error Count: {err_count}')
print(f'Failed Chunks Count:  {failed_chunks}')
assert exec_commit != 'NOT_RECORDED', 'ATTENZIONE: execution_software_commit non registrato!'
assert err_count >= failed_chunks, 'ATTENZIONE: error_count inferiore ai chunk falliti!'
print('Verifica report superata con successo!')
"
```

--------------------------------------------------------------------------------
7. PROCEDURA DI RECOVERY SELETTIVO PER CHUNK FALLITI
--------------------------------------------------------------------------------
Se al termine dell'esecuzione rimangono chunk falliti (es. a causa di sovraccarico di VRAM
o riavvio demone LM Studio):

1. NON cancellare la cartella `.checkpoints`.
2. I chunk completati con esito SUCCESS risiedono intatti nei file checkpoint.
3. Riavviare l'analisi abilitando `enable_checkpointing=True` e `resume_run_id=<RUN_ID>`.
4. Il sistema verificherà crittograficamente la compatibilità (stesso modello, stesso prompt template,
   stesso chunk plan e checksum dataset).
5. I chunk già riusciti verranno caricati con provenienza `RECOVERED_CHECKPOINT`.
6. Verranno re-inferiti ESCLUSIVAMENTE i chunk precedentemente falliti.
7. È severamente proibito fondere checkpoint tra modelli differenti (es. Qwen con Llama)
   o con chunk plan differenti: in tali casi il preflight bloccherà l'operazione per prevenire
   inquinamento dei dati forensi.
